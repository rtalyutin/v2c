# v2c

Серверный MVP для преобразования незнакомого работающего проекта в проверяемую кодовую базу и передачи навыков её сопровождения владельцу. Основание: ТЗ 0.9 от 18.10.2026 (§15–16). LeraBack — первый проверочный случай, общий механизм не назначает проектам одинаковый framework или ORM.

## Что реализовано

- Закрытый API и операторская панель: проекты, архивы/комплекты репозиториев, снимки, запуски, план, решения, остановка, контрольная доработка, человеческая приёмка и скачивание пакета.
- SQLAlchemy/Alembic, PostgreSQL, типизированные метаданные прикладных сущностей, долговечные этапы/попытки/команды/свидетельства.
- PostgreSQL-очередь, один активный запуск, максимум **пять попыток на логический шаг**, согласование конкретной версии плана, lease и защита от устаревших исполнителей.
- Открытый модельный порт и OpenAI-совместимый HTTP-адаптер; endpoint/model/ссылка на секрет задаются сервером. Автоматического выбора провайдера нет.
- Импорт ZIP/TAR, внутренний Git, закреплённые SHA нескольких репозиториев, неизменяемые объекты и исходные Git bundles. Local storage для разработки и S3 adapter для серверной поставки.
- Цикл inspect → baseline → plan → согласование → изменения → новая проверочная среда → пакет-кандидат → контрольная доработка новым ИИ → приёмка разработчиком.
- Runner для **отдельной одноразовой VM**: mTLS, журнал команд до исполнения, идемпотентная доставка, ограниченный Docker, чтение результата, подтверждение остановки.
- Поставка кода, Git bundles, документации, проверок и шести проектных навыков. Универсальный преобразователь в пакет проекта не включается.

Готовность конкретного проекта не следует из наличия этих компонентов. Она подтверждается его фактическими проверками. Если интеграция не подключена или сценарий среды не поддержан, запуск получает `NEEDS_INPUT` с причиной; тестовый двойник не выдаётся за преобразование проекта.

## Локальный запуск управления

Нужны Python 3.12+ и Git. Docker и модельный API для открытия панели и проверки ядра не требуются.

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install --no-deps -e .
export V2C_DATABASE_URL=sqlite:///./data/v2c.db
export V2C_STORAGE_BACKEND=local
export V2C_API_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
mkdir -p data
alembic upgrade head
uvicorn v2c.api:app --host 127.0.0.1 --port 8000
```

Откройте `http://127.0.0.1:8000`, введите настроенный ключ оператора. Ключ страницы хранится в памяти вкладки, не в localStorage. Во втором терминале с теми же переменными:

```bash
python -m v2c.worker
```

SQLite поддерживается как локальная среда разработки. Серверный профиль использует PostgreSQL; его межпроцессные гарантии проверяются отдельным тестом и в CI. API не создаёт схему автоматически: миграции применяются отдельно.

## Серверная конфигурация

`compose.yaml` размещает управление, worker, PostgreSQL и мигратор. S3 подключается отдельно. Скопируйте `.env.example` в `.env`, заполните значения и следуйте [инструкции развёртывания](docs/deployment.md). Секреты и сертификаты не входят в Git.

Среда управления и среды проекта разделены. Нельзя давать API/worker Docker socket для исполнения входящих проектов. Каждый этап исполнения получает отдельную VM через реализованный клиент REST-протокола VM lifecycle. Сам шлюз к конкретному облаку выбирается/подключается оператором; его адрес и mTLS необходимы для настоящего прохода. Протокол: [runner-protocol.md](docs/runner-protocol.md).

В образе проекта нужен Python 3 для безопасного применения файловых изменений и нужные ему runtime/зависимости. Образ закрепляется digest. Это ограничение среды исполнения первой версии; язык входящего проекта не переписывается. Сеть проекта по умолчанию закрыта; зависимости должны быть доступны через подготовленный профиль образа/сервисов.

Настройки модели:

| Переменная | Значение |
|---|---|
| `V2C_MODEL_BASE_URL` | HTTPS base URL совместимого API, обычно с `/v1` |
| `V2C_MODEL` | Идентификатор модели |
| `V2C_MODEL_API_KEY_ENV` | Имя серверной переменной с ключом |
| `V2C_MODEL_PROFILE_VERSION` | Версия профиля, фиксируется в запуске |
| `V2C_VM_PROVIDER_URL` | HTTPS endpoint внешнего шлюза VM lifecycle |
| `V2C_RUNNER_*CERT*`, `V2C_RUNNER_CLIENT_KEY` | Пути mTLS материалов в управлении |
| `V2C_GIT_ALLOWED_HOSTS` | Разрешённые оператором HTTPS Git hosts |

Первый модельный wire profile — `POST {base}/chat/completions`, JSON Schema response, `max_tokens`, без streaming/tool execution. У API/модели с другим протоколом требуется другой адаптер или проверенное расширение профиля. Скрытых SDK-повторов нет. Провайдер может списать стоимость запроса с потерянным ответом: неизвестное использование не превращается в ноль.

Профили времени/памяти/вывода — технические пределы из конфигурации, не обещание SLA. Пять попыток не ограничивают число шагов или всю стоимость проекта. Изменять лимиты уже начатого запуска скрытно нельзя. При первом модельном запросе фиксируется полный профиль без значения секрета; смена endpoint, модели или возможностей требует нового запуска. Отсутствующая до подключения модель может быть настроена позже.

## API

Контракт HTTP публикуется самой сборкой в `/openapi.json`; интерактивная документация — `/docs`. Все операции с проектами требуют `Authorization: Bearer ...` и проверки владельца. Для нескольких операторов `V2C_OPERATOR_TOKENS` задаёт JSON-словарь `owner_id → token`; ключи минимум 24 символа, без повторов.

| Операция | Назначение |
|---|---|
| `POST /projects` | Создать проект |
| `POST /projects/{id}/imports` | Тело ZIP/TAR как octet-stream; либо JSON repositories с name/url/revision/secret_ref |
| `GET /projects/{id}/snapshots` | Снимки импортированных версий |
| `POST /projects/{id}/runs` | snapshot_id + idempotency_key |
| `GET /runs/{id}`, `/events`, `/plan` | Состояние, журнал, план |
| `POST /runs/{id}/decisions` | snapshot_id + plan_revision + approved |
| `POST /runs/{id}/cancel` | Запросить остановку; CANCELLED только после подтверждения |
| `POST /runs/{id}/resume` | Продолжить после предоставления недостающей конфигурации |
| `POST /runs/{id}/acceptance` | Отдельное задание новому ИИ и скрытые от него команды проверки |
| `POST /runs/{id}/handoff` | final_digest + passed + свидетельство отдельного разработчика |
| `GET /runs/{id}/artifacts` | Пакеты и свидетельства, включая статус кандидата |

Импорт не принимает путь к файлу на сервере. Удалённый Git требует allowlist и точный 40-символьный SHA; токен передаётся ссылкой вида `env:VARIABLE`, не в URL. Загрузка ограничена до разбора и при распаковке.

## Проверка и границы evidence

```bash
python -m pytest -q
```

Тесты используют временные БД/объекты, реальные локальные Git bundles и управляемые двойники HTTP/VM/Docker. Они проверяют повторы, потерянные ответы, fencing, отмену, авторизацию, безопасный импорт и целостность поставки. Для реального PostgreSQL отдельно задайте `V2C_TEST_POSTGRES_URL` к **выделенной тестовой БД**, уже обновлённой Alembic. CI поднимает отдельный PostgreSQL.

Модельные вызовы, облачный VM lifecycle, Docker isolation, настоящие S3 и mTLS, перенос LeraBack и другого проекта, человеческая доработка и стоимость требуют сквозного испытания подключённой среды. Они не объявляются пройденными по unit/contract tests. Неполная приёмка оставляет пакет кандидатом; только согласованные свидетельства одной конечной версии позволяют READY.

После AI- и человеческой приёмки формируется запечатанный пакет: код и навыки сохраняются, добавляются итоговые receipts и их проверяемый манифест. `READY` требует точного совпадения последних четырёх свидетельств с этим пакетом. Новое обязательное свидетельство делает прежнее запечатывание неактуальным.

## Структура

`engine.py` владеет состояниями и транзакциями; `pipeline.py` связывает этапы; `adapters/` содержит внешние порты; `runner_service.py` исполняется в выделенной VM; `intake.py`, `storage.py`, `delivery.py` владеют входом, объектами и поставкой. `api.py` и `web/` — управление. Это один модульный backend и отдельный процесс worker.
