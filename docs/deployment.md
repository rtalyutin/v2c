# Развёртывание v2c

Этот репозиторий содержит сервер управления и отдельный сервис исполнения.
Приложение клиента запускается только на выделенной одноразовой VM.
`compose.yaml` поднимает управление; опциональный профиль `timeweb-gateway`
поднимает шлюз Timeweb. Сам runner в этот Compose не входит.
Публикация кода и успешные тесты не означают, что инфраструктура развёрнута.

## Локальная разработка

Требуется Python 3.12+. SQLite и файловые артефакты подходят для локальной
разработки API и тестов. Они не проверяют PostgreSQL, S3 или изоляцию VM.

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install --no-deps .
export V2C_API_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export V2C_DATABASE_URL=sqlite:///./data/v2c.db
export V2C_STORAGE_BACKEND=local
mkdir -p data
alembic upgrade head
uvicorn v2c.api:app --host 127.0.0.1 --port 8000
```

Рабочий процесс запускается отдельным процессом с теми же переменными:
`python -m v2c.worker`. Без реального модельного API и VM-provider endpoint
сквозное преобразование не выполняется. Тестовые адаптеры используются только
тестами и не подтверждают результат реального проекта.

## Управляющая VM

Нужны Docker Engine, Compose >= 2.24 и отдельное приватное S3-совместимое
хранилище. PostgreSQL запускается в Compose и не публикует порт на VM.

1. Скопировать `.env.example` в `.env`, ограничить доступ: `chmod 600 .env`.
2. Задать `V2C_API_TOKEN` длиной от 24 символов и
   `V2C_POSTGRES_PASSWORD`. Для пароля PostgreSQL использовать случайную
   hex-строку, чтобы не требовалось кодировать специальные символы в URL.
3. Для этого развёртывания явно задать `V2C_STORAGE_BACKEND=s3`,
   `V2C_S3_ENDPOINT_URL`, `V2C_S3_BUCKET`, `V2C_S3_PREFIX`,
   `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`. Создать приватный bucket.
   Ключ приложения должен иметь доступ только к нужному bucket/prefix.
4. Сохранить CA, сертификат клиента и его ключ в `certs/`. Права должны
   разрешать чтение UID 10001 контейнера и запрещать посторонний доступ.
   Задать пути в контейнере, например `/run/v2c-certs/client.key`.
   Каталог существует до запуска даже при ещё не подключённом runner.
5. Проверить конфигурацию и запустить управление:

```sh
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 migrate api worker
```

В Compose URL БД собирается для внутреннего сервиса `postgres`; локальный
`V2C_DATABASE_URL` из `.env` не перенаправляет его на SQLite.
API доступен по `127.0.0.1:8000`; для внешнего доступа поставить HTTPS-прокси
перед ним. Не выставлять PostgreSQL, S3 admin console или runner в Интернет.
Токены передаются в `Authorization: Bearer ...`, а не в URL.

Каталог `/data` — отдельный том управления. В нём остаются рабочие копии;
S3 содержит подтверждённые артефакты. Настроить резервное копирование
PostgreSQL и объектного хранилища вместе с проверкой восстановления.
До обновления схемы сделать резервную копию. Команда `alembic upgrade head`
запускается отдельным сервисом до API и worker. Откат контейнера сам по себе
не откатывает миграцию. Не выполнять `docker compose down -v` для сохранения
данных.

## Модель

Задать `V2C_MODEL_BASE_URL` — корень OpenAI-совместимого API,
`V2C_MODEL` и `V2C_MODEL_API_KEY_ENV` — имя переменной с ключом.
По умолчанию имя — `V2C_MODEL_API_KEY`; сам ключ хранится только в окружении
управления. Дополнительную переменную с выбранным именем можно передать
через `.env`; Compose загружает её в API/worker. Профиль и поддерживаемые
возможности проверяются адаптером, а не определяются по названию модели.

Вызовы ограничены таймаутами, размерами входа/ответа и числом попыток.
Пять попыток на шаг включают первоначальную; это не денежный бюджет.
Платные вызовы и provisioning VM не запускаются тестами по умолчанию.

## Runner на отдельной VM

Операторский VM-provider endpoint обязан реализовать протокол из
`docs/runner-protocol.md`: создание VM по сохранённому `allocation_id`,
чтение состояния и подтверждаемое уничтожение. Реализация для Timeweb Cloud,
шаблон VM и параметры находятся в [timeweb.md](timeweb.md). Другой облачный
провайдер требует своей реализации общего контракта. Одна заранее созданная VM
управления не заменяет новые VM для исполнения и итоговой проверки.

На образе runner установить Python, этот пакет и Docker. Runner daemon
имеет полномочия Docker только внутри своей одноразовой VM. Проектный
контейнер запускается без Docker socket, privileged, host network и ключей
управления. На уровне гипервизора/облачной сети блокировать доступ VM к
управлению, metadata service и другим проектам; разрешать вход только от
управления. Доступ проекта в сеть по умолчанию отсутствует.

Образ проектного runtime выбирает оператор по digest. Он должен содержать
нужные зависимости; автоматическое выполнение присланного Dockerfile с
правами Docker daemon не предусмотрено. JSON-конфигурация runner хранится
за пределами проектного каталога. Пример структуры:

```json
{
  "data_dir": "/var/lib/v2c-runner",
  "bearer_secret": "REPLACE_WITH_RANDOM_SECRET_AT_PROVISIONING",
  "image": "registry.example/runtime@sha256:REPLACE_WITH_64_HEX_DIGEST",
  "cpu_limit": 1,
  "memory_bytes": 1073741824,
  "pids_limit": 128,
  "tmpfs_bytes": 67108864,
  "workspace_disk_bytes": 536870912,
  "max_archive_bytes": 67108864,
  "max_expanded_bytes": 268435456,
  "max_files": 20000,
  "max_command_seconds": 120,
  "max_output_bytes": 65536,
  "uid": 10001,
  "gid": 10001,
  "postgres_image": null
}
```

Плейсхолдер digest намеренно не проходит валидацию. В примере сервис БД
выключен. Для PostgreSQL задать `postgres_image` с digest и явно указать
`postgres_data_bytes`, `postgres_ready_seconds`, `postgres_uid`,
`postgres_gid`. UID/GID должны подходить выбранному образу, который обязан
поддерживать `PGDATA=/pgdata` без root. Образы заранее загружаются на VM.
Запрашиваемый `V2C_RUNNER_DISK_MB` управления должен покрывать размер
файловой системы runner и `postgres_data_bytes` вместе. Например, 512 MiB
для файлов и 256 MiB для тестовой БД требуют не менее 768 MiB в профиле.

`data_dir` должен
находиться на отдельной файловой системе с общей ёмкостью не больше
`workspace_disk_bytes`; runner проверяет эту границу и откажет при её
отсутствии. Журнал команд должен переживать перезапуск процесса. Права и
дисковая квота задаются при создании VM, до загрузки клиентского проекта.

```sh
python -m v2c.runner_service \
  --config /operator/runner.json \
  --tls-cert /operator/server.crt \
  --tls-key /operator/server.key \
  --client-ca /operator/control-ca.crt \
  --port 8443
```

CLI требует взаимную проверку TLS-сертификатов. Передать управлению
`V2C_RUNNER_SERVER_NAME`, `V2C_RUNNER_TOKEN`, `V2C_RUNNER_CA_CERT`,
`V2C_RUNNER_CLIENT_CERT`, `V2C_RUNNER_CLIENT_KEY`, а также
`V2C_VM_PROVIDER_URL` и `V2C_VM_PROVIDER_TOKEN`. Фактический адрес runner
приходит в `VMAllocation.runner_endpoint`; `V2C_RUNNER_BASE_URL` его не задаёт.
Таймаут команды требует чтения её состояния; при неизвестном исходе
нельзя повторять её на той же VM. Восстановление — после подтверждения
остановки/уничтожения прежней VM и воспроизведения тестовой БД.

`--config` можно опустить: runner прочитает `V2C_RUNNER_SETTINGS_FILE` или
поля `V2C_RUNNER_<FIELD>` из своего окружения. TLS-аргументы CLI обязательны
в любом режиме. Эти переменные настраиваются на runner VM; их не следует
копировать как секреты тестовой БД в окружение управления.

Поддерживается один синтетический сервис PostgreSQL на workspace. Он
работает в собственной внутренней сети без опубликованных портов; проект
получает только сгенерированный тестовый `DATABASE_URL`. При восстановлении
на новой VM БД пересоздаётся из миграций и синтетических fixtures по рецепту
с обязательными recovery checks. ZIP checkpoint содержит файлы проекта,
а не снимок БД. Другие сервисы и произвольный Compose проекта пока требуют
отдельного расширения протокола.

## Необязательный локальный S3

Профиль `local-s3` предназначен для проверки S3-совместимости. В октябре
2026 официальный README MinIO указывает, что community-репозиторий не
поддерживается и распространяется как исходный код. Поэтому Compose
не скачивает старый образ автоматически. Оператор задаёт проверенный
`V2C_MINIO_IMAGE` со своим digest/сборкой; инструкция сборки — в
[официальном README](https://github.com/minio/minio#build-docker-image).

Задать отдельные `V2C_MINIO_ROOT_USER`/`V2C_MINIO_ROOT_PASSWORD`, запустить
`docker compose --profile local-s3 up -d minio`, создать приватный bucket
и отдельный ключ приложения. Для контейнеров endpoint — `http://minio:9000`.
Порты 9000/9001 привязаны только к localhost. Для развёрнутого сервиса
использовать поддерживаемое приватное S3-хранилище с TLS.

## Проверка поставки

GitHub Actions выполняет тесты на Python 3.12, миграцию чистой PostgreSQL,
проверку Compose и сборку управляющего образа на одной ревизии. Тесты не
получают облачных или модельных ключей; workflow не разворачивает сервис.
Действия закреплены по SHA, токен имеет только `contents: read`.

Для приёмки развёртывания отдельно подтвердить сохранение артефактов в S3,
сбой и восстановление worker, отмену с остановкой VM, новый runner для
итоговой проверки и реальное выполнение проекта. Результат LeraBack и
второго незнакомого проекта, а также доработка новым ИИ и разработчиком
требуют отдельных приёмочных свидетельств.
