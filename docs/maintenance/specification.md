# v2c: оценка руководителя разработки и ТЗ на сопровождаемость

Дата: 27.10.2026, Москва. Версия документа: 1.0.

Объект: [rtalyutin/v2c](https://github.com/rtalyutin/v2c), ветка `main`, commit [`bea8639471537fb9c181089cdb027d69e31a041b`](https://github.com/rtalyutin/v2c/commit/bea8639471537fb9c181089cdb027d69e31a041b).

Статус: аудит выполнен, ТЗ подготовлено. Изменения кода, настроек GitHub и развёртывания не выполнялись. ТЗ относится к **самому v2c**, а не к проектам, которые он преобразует.

## 1. Управленческий вывод

**v2c можно сопровождать человеком уже сейчас, но передача новому разработчику потребует слишком много восстановления скрытых связей. Оценка сопровождаемости — около 5/10.** Это инженерная оценка по перечисленным ниже основаниям, не стандартизированный индекс и не результат эксперимента с человеком.

Проблема не в выбранном стеке и не в отсутствии тестов. Проект содержит полезный фундамент: FastAPI, SQLAlchemy/Alembic, зафиксированные зависимости, отделённое исполнение недоверенного кода, долговечные состояния и содержательные проверки отказов. Но правила и технические механизмы сконцентрированы в крупных классах; многие внутренние контракты существуют только как соглашения о ключах словарей. Чтобы безопасно изменить один участок, разработчик должен держать в голове значительную часть системы.

Рекомендация руководителя разработки: **сохранить стек и процессы, провести постепенный рефакторинг с проверкой совместимости после каждого шага**. Полная перепись, переход к микросервисам, новая универсальная система workflow или замена ORM не обоснованы целью этой работы.

| Область | Оценка | Основание |
|---|---:|---|
| Понимание архитектуры и границ изменения | 5/10 | Общая структура описана, но `Pipeline` и `Engine` требуют широкого контекста |
| Контракты и помощь IDE | 4/10 | На внешних адаптерах есть типы; ядро передаёт нетипизированные словари, ответы операторского API не описаны |
| Защита от регрессий | 7/10 | 196 тестов в CI; есть проверки повторов, конкуренции, fencing, восстановления и принадлежности данных |
| Вход нового разработчика | 5/10 | Локальный запуск описан; нет самостоятельного руководства по внесению изменений и проверенного человеческого onboarding |
| Диагностика неожиданного сбоя | 4/10 | Долговечный журнал есть, но worker скрывает даже класс и место неожиданной ошибки |
| Предотвращение нового технического долга | 4/10 | CI запускает тесты и сборку; статические проверки и обязательность CI для `main` не закреплены |

Размеры файлов — указатели для чтения, а не самостоятельное доказательство плохой архитектуры. Оценка основана на сочетании размеров, смешения обязанностей, неявных контрактов и результатов проверок.

- Получена актуальная на момент проверки `main`; локальный SHA совпал с GitHub.

## 3. Что сохранить

1. Разделение управления и исполнения: API/worker не исполняют код входящего проекта; runner работает в отдельной VM.
2. Журналирование намерения до внешнего эффекта, стабильные идентификаторы команд и проверку результата при потерянном ответе.
3. Lease/generation fencing, защиту от устаревшего исполнителя и ограничение пяти попыток на логический шаг.
4. Согласование конкретных snapshot/plan revision и ограничение изменений разрешёнными путями.
5. Проверку владельца, контроль архивов, хешей и неизменности исходников при выполнении проверок.
6. Раздельные свидетельства регрессии, восстановления, ИИ-доработки и человеческой передачи; `READY` только для соответствующего запечатанного пакета.
7. Различение реальных интеграций и тестовых двойников, неизвестного результата и подтверждённого успеха.
8. Существующие тесты, lock-файл, миграции и воспроизводимый CI. Дополнять их, а не заменять несколькими smoke-тестами.

## 5. Техническое задание

### 5.1. Цель и границы

Цель: новый Python-разработчик получает репозиторий, запускает его, находит владельца нужного поведения, делает ограниченное изменение и доказывает отсутствие регрессии без доступа к истории создания проекта.

Обязательный объём: M01–M10. Новые продуктовые функции, изменение бизнес-правил, масштабирование числа одновременно работающих запусков, смена фреймворка/ORM/модельного провайдера, редизайн панели и переписывание входящих клиентских проектов не входят.

Сохраняются публичные URL, CLI/модульные точки запуска, значения статусов, ошибки, формы действующих данных и протоколов. Если в ходе работы выявляется необходимое изменение поведения, оно оформляется отдельным дефектом/решением и не маскируется под перенос файлов.

### 5.2. Целевые границы модулей

Ниже — предлагаемая структура ответственности, а не требование создать максимальное число файлов. Соседние короткие реализации допускается оставить вместе, если у них один владелец правил и понятный интерфейс.

| Граница | Ответственность | Зависимости |
|---|---|---|
| `contracts/` | Публичные HTTP DTO, runner/provider DTO, внутренние типы claims/results; отдельные типы для разных границ | Pydantic/stdlib; без ORM, FastAPI handlers, облачных клиентов |
| `workflow/` | Переходы run/step/attempt, lease/fencing, retry policy, completion rules | Внутренние контракты, транзакционные операции persistence |
| `persistence/` | ORM, запросы, транзакции, проекты/метаданные, команды/свидетельства | SQLAlchemy и внутренние типы; без HTTP/VM/model вызовов |
| `orchestration/` | Стадии inspect/baseline/plan/transform/verify/package/handoff, порядок выполнения | workflow, узкие порты, источники/поставка |
| `sources/`, `delivery/` | Безопасный импорт, архивы, Git, checkpoints и пакеты | Файловые/объектные операции; явно публичные общие функции |
| `adapters/` | Конкретные модель, VM provider, runner client, object storage | Протоколы/DTO соответствующих границ |
| `api/`, `worker.py` | HTTP и процессный запуск, сборка зависимостей | Прикладные сценарии; без собственной версии правил workflow |
| `runner/`, `providers/timeweb/` | Отдельные действующие контуры исполнения и lifecycle | Собственные журналы, wire contracts; без импорта control-plane ORM |
| `web/` | HTTP-клиент, состояние выбранного проекта/запуска, polling, рендер | Публичный HTTP-контракт |

`api.py`, `pipeline.py`, `engine.py`, `runner_service.py`, `timeweb_gateway.py` могут временно сохраняться как совместимые фасады старых точек входа. Срок/условие удаления каждого фасада фиксировать. Не вводить generic repository, service locator, DI-framework или динамическую систему плагинов без конкретной потребности.

### M01. Воспроизводимая разработка и обязательные проверки — P0

**Изменить:** `pyproject.toml`, зависимости разработки, CI, команды разработчика; настройки GitHub оформить отдельной операцией при внедрении.

1. Предоставить одну документированную команду установки dev-среды и одну команду `check`, одинаковую локально и в CI. Отдельно — быстрые тесты без облака и интеграционные проверки PostgreSQL/Compose.
2. Подключить Ruff для форматирования/ошибок и mypy для типов, закрепить совместимые версии. Сначала форматирующий PR без изменения поведения; затем исправления. Новые и выделенные модули проверять строго; для старых допускается конкретный временный baseline с перечнем исключений, без глобального отключения диагностики.
3. Отделить dev/test зависимости от production install либо документировать переходный lock-профиль. Зафиксировать команду и версию генератора lock; новый инструмент lock выбирать лишь при установленной необходимости.
4. В CI включить checks, pytest, PostgreSQL migration/schema comparison, Compose/build, контрактный diff. Проверка миграций должна обнаруживать незакоммиченные изменения модели.
5. Для `main` предложить обязательный PR и успешные checks перед merge. Не требовать фиктивного второго человека при отсутствии команды; режим обхода, если нужен владельцу, документируется отдельно.

**Приёмка:** чистый checkout устанавливается по одной инструкции; локальный и CI `check` используют одну конфигурацию; контрольная ошибка линтера/типа/миграции действительно блокирует соответствующий check. Невозможно получить успешный обязательный CI за счёт пропуска PostgreSQL/Compose. Изменение правил GitHub проверяется чтением применённого ruleset, а не наличием YAML в репозитории.

### M02. Явные публичные контракты — P0

**Изменить:** operator API, выходные DTO, сериализацию, экспорт OpenAPI и контрактные тесты.

1. Описать успешные ответы проектов, snapshots, runs, steps, events, plans, usage, artifacts и handoff. Для JSON-полей определить обязательность, `null`, семантику, единицы времени/размера и идентификаторы. Не заменять неизвестные значения нулями.
2. Развести внутренний ORM DTO и публичный DTO. Поля наружу выбираются явно; фильтр `public()` может остаться дополнительной защитой, но не определяет схему ответа.
3. Описать ошибки 401/404/409/413/422/503 там, где они фактически возможны, и две формы импорта: JSON repositories и binary archive. Уточнить фактический формат `GET /plan` при отсутствии плана — сохранить текущее `null`.
4. Для скачивания указать `application/zip` и binary response, сохранить заголовки/проверку целостности.
5. Canonical source — Pydantic/FastAPI, режим code-first. OpenAPI генерируется из кода, не редактируется вручную. Хранить экспорт/команду генерации; CI проверяет отсутствие drift и явность несовместимого изменения.

**Приёмка:** все 19 существующих успешных response entries описаны корректно; бизнес-DTO не являются пустым `{}` или произвольным объектом целиком. Расширяемые metadata-поля могут оставаться словарями с обозначенной ролью. Данные baseline проходят новые схемы без переименования/потери полей; лишняя ORM-колонка автоматически не становится публичным полем. Корректный и намеренно нарушенный ответы проверяются независимым валидатором схемы.

### M03. Типы и порты внутренних взаимодействий — P1

1. Ввести минимальные типы `RunClaim`, `AttemptFence`, `ArtifactRef`, `ExecutionLimits`, а также типизированные результаты этапов. Не навязывать один DTO транспорту, домену и ORM. Для существующих JSON-форматов применять совместимые TypedDict/модели и адаптеры.
2. Определить Protocol для реально используемых операций runner и VM provider. Повторно использовать существующие `ModelPort` и `ArtifactStore`.
3. Убрать `Any` и неструктурированные `dict` на перечисленных границах. `Any` допустим в узком декодере чужого JSON до валидации, но не как интерфейс orchestration.
4. Дать публичные имена общим Git/inventory функциям. Для собственного `DeliveryBundle` оставить единственный документированный контракт; альтернативные ключи удалить только после проверки существующих сохранённых данных/потребителей.

**Приёмка:** IDE показывает состав claim/results и доступные методы портов; type check обнаруживает опечатку поля и отсутствие метода тестового адаптера до запуска. Старые persisted payloads читаются. Хеши и идентификаторы неизменяемых операций не меняются вследствие сериализации, defaults, enum или `null`.

### M04. Разделение Pipeline и прикладных сценариев — P1

1. Выделить операции модели и упаковки контекста; lifecycle VM и команд; операции checkpoints/архивов; сборку и запечатывание поставки. Стадии должны читаться как последовательность этих операций.
2. Вынести импорт и человеческий handoff из HTTP handlers в прикладные сценарии. HTTP оставляет разбор входа, auth/owner check, вызов сценария и отображение результата/ошибки.
3. Заменить неявную диспетчеризацию `getattr('_stage_' + kind)` явным реестром поддерживаемых стадий либо равноценной статически проверяемой конструкцией. Все предусмотренные виды стадий обязаны иметь обработчик; неподдерживаемое значение даёт прежний контролируемый отказ.
4. Не менять устойчивые operation IDs, порядок «записать намерение → вызвать → прочитать результат», fencing, cleanup и семантику UNKNOWN. Транзакции не охватывают HTTP/model/VM вызовы.

**Приёмка:** новая стадия или изменение существующей не требует редактирования модельного HTTP, ZIP-кода и lifecycle VM. Тест стадии запускается через порты без настоящего облака. Прежние fault-сценарии продолжают проходить; отдельно проверены потерянный ответ, restart между записью/dispatch/readback, устаревшая generation и неподтверждённая остановка. Формальное дробление класса с общим изменяемым контекстом результатом не считается.

### M05. Правила состояния и транзакционная граница — P1

1. Разделить обслуживание проектов/метаданных, run/step/attempt, команд и свидетельств. Сохранить общий владелец транзакции там, где проверка и запись должны быть атомарны; не разбивать атомарный переход на несколько независимых commits.
2. Для run, step, attempt и command вести **раздельные** множества состояний и правил перехода. В частности, `STOPPED` управления и состояния wire-протокола runner не объединять механически.
3. Составить таблицу «входное состояние + событие + guards → состояние + DB-эффекты + разрешённые внешние действия». Связать её с кодом и параметризованными тестами. Не создавать универсальный workflow DSL.
4. Централизовать правила retryability и terminality в пределах соответствующего домена. UI отображает возможности, но сервер остаётся источником разрешений.
5. EAV оставить за интерфейсом метаданных, не менять схему только ради эстетики. Сохранить единственный активный запуск и существующую блокировку в этом объёме.

**Приёмка:** для каждой изменённой ветки есть разрешённый и запрещённый переход; повтор события не создаёт новый эффект. PostgreSQL-тесты подтверждают конкуренцию двух workers, ровно пять попыток, fencing и атомарную фиксацию перехода. Готовность пакета не возникает из одного успешного шага или неподтверждённой остановки.

### M06. Диагностика, пригодная для человека — P0

1. Добавить структурированные записи с `event`, `error_class`/безопасным кодом, `worker_id`, и доступными `run_id`, `step_id`, `attempt_id`, `generation`, `command_id`/`allocation_id`. Недоступный контекст оставлять отсутствующим, а не выдумывать.
2. Для неожиданных ошибок сохранять безопасную цепочку места возникновения: модуль/функция/строка. Не включать локальные переменные, токены, полные URL с credentials, текст исходников или сырой exception message от провайдера.
3. Связать журнал с инструкцией диагностики: какие состояния/команды читать, когда допустимо resume, когда требуется readback и почему нельзя просто повторить внешний вызов.
4. Сохранить fail-closed поведение; улучшение логов не разрешает новый retry или перевод в успех.

**Приёмка:** синтетические ошибки БД/хранения/программы различимы; по журналу находится соответствующая операция без ручного просмотра всей БД. Контрольные секреты в exception message/URL/body не попадают в лог. Состояния и число внешних вызовов совпадают с baseline для тех же отказов.

### M07. Обслуживание runner/gateway и совместимость журналов — P1

1. Разделить journal, Docker/HTTP adapter, lifecycle policy и API внутри существующих процессов. Не переносить runner в API/worker и не менять сетевую границу.
2. Ввести явную версию SQLite-схемы, например `PRAGMA user_version`, и проверку совместимости при открытии. Текущая неверсионированная схема распознаётся по структуре и получает версию без потери данных.
3. Предоставить ограниченный migration path и fixtures предыдущего журнала; несовместимая более новая схема останавливает сервис с диагностикой. Для долговечного gateway сделать резервную копию до изменения; для одноразового runner описать замену VM с сохранением учёта неизвестного исхода.
4. Не унифицировать два журнала общим framework: их жизненный цикл и гарантии различаются.

**Приёмка:** legacy journal с ACCEPTED/RUNNING/UNKNOWN и pending delete открывается/обновляется согласно контракту; перезапуск не повторяет CREATE или выполнение команды. Потерянная запись не трактуется как отсутствие внешнего эффекта. Ошибка миграции и неизвестная версия не приводят к автоматическому созданию пустого журнала.

### M08. Читаемый исходный код операторской панели — P1

1. Отформатировать JS/HTML, вынести CSS. Разделить HTTP-client, состояние/выбор проекта и запуска, polling и render в небольшие ES-модули по необходимости.
2. Сохранить текущую визуальную структуру и все действия; новый frontend framework не нужен для этой задачи.
3. При изменении polling добавить отмену или проверку поколения запроса: поздний ответ старого проекта/запуска не должен затирать новый выбор; logout прекращает обновления и не восстанавливает закрытый сеанс.
4. Добавить минимальные браузерные проверки пользовательских сценариев с управляемыми HTTP-ответами. Выбор и версии тестового инструмента фиксируются в lock, если он добавляется.

**Приёмка:** diff читается построчно, изменение API-клиента не требует правки DOM-render. Проверены login/logout, импорт, выбор запуска, решение по плану, cancel/resume, acceptance/handoff, download; отдельно — задержанный старый ответ и сетевой отказ. Ключ остаётся только в памяти вкладки. Новая проверка гонки не считается доказательством, что эта гонка наблюдалась в production до рефакторинга.

### M10. Проверка человеческой передачи — обязательный финальный gate

Автоматические проверки не подтверждают, что код стал удобнее человеку. Финальная приёмка выполняется Python-разработчиком, который не участвовал в рефакторинге и не читает историю разговоров/подсказки автора.

Предлагаемый критерий готовности, подлежащий принятию вместе с ТЗ:

1. Из чистого checkout по README/CONTRIBUTING запустить API и локальные тесты не более чем за **60 минут** активной работы. Сетевое ожидание установки учитывать отдельно.
2. За **30 минут** найти владельцев правил retry, fencing, approval, READY и показать конкретные файлы/тесты.
3. Выполнить заранее не показанную автору рефакторинга небольшую доработку за **2 часа** активной работы, включая тест. Класс задачи: добавить необязательное диагностическое поле в ответ и отображение либо изменить одну изолированную валидацию. Конкретный вариант и ожидаемый результат готовит принимающий после заморозки версии.
4. По заранее внедрённому безопасному отказу за **30 минут** определить этап, операцию и допустимое действие восстановления, не меняя DB вручную.

Для чистоты первого измерения — без ИИ-помощника, с документацией репозитория и обычной документацией библиотек. Если проверка с ИИ нужна рабочему процессу, провести её отдельно и не смешивать результаты.

**Свидетельство:** SHA, среда, опыт проверяющего, задание, время, все вопросы/подсказки, diff и результаты независимых проверок. При непрохождении исправляются обнаруженные причины и повторяется другая сопоставимая задача. Снижение порогов после результата не превращает провал в успех. Временные пороги здесь — предлагаемые требования, не уже измеренная скорость работы.

## 6. Контракты и миграция

**Contract delta:** цель — сохранение текущего wire/поведения с добавлением явной схемы, типов и диагностики. JSON для скачивания в OpenAPI исправляется на фактический ZIP; это исправление спецификации. Новые продуктовые поля или изменение ошибок не разрешаются этим документом автоматически.

**Revision:** исходный контракт и fixtures закрепить за `bea8639`. Существующий runner `/v1` остаётся `/v1` при совместимых изменениях. Генератор OpenAPI — текущая закреплённая FastAPI/Pydantic-сборка; команду экспорта и config добавить в M02. Async-взаимодействия — не брокер сообщений, а durable команды/HTTP readback; их request/result schemas и правила повторов документируются отдельно.

**Sequence:** порядок эффектов должен сохраняться. Обновить схемы последовательности для approval, dispatch/readback/recovery, cancel и handoff. Их отсутствие сейчас не объявлять `N/A`.

Порядок перехода:

1. Заморозить baseline: API fixtures, пример БД, journals, bundles/checkpoints и результаты тестов на синтетических данных. Не выгружать секреты или production-исходники.
2. Вводить типы и фасады поверх текущего поведения. Проверять чтение старых JSON без пересчёта идентичностей/хешей.
3. Переносить по одной обязанности; не смешивать форматирование, смену поведения и миграцию данных в одном PR.
4. До выкладки остановить выдачу новых работ, завершить/остановить активные с подтверждением и сохранить неизвестные исходы. Допускается поэтапное обновление control/gateway/runner только при доказанной совместимости обеих версий; иначе — согласованное окно обслуживания.
5. Сохранять чтение предыдущего формата на период перехода. Миграции — additive, где возможно. Для изменения формата без обратного чтения заранее определить backup/restore и версию бинарника; rollback кода сам по себе не откатывает схему.
6. После каждого PR повторить затронутые проверки; перед итоговой приёмкой — весь согласованный набор. Не запускать реальные VM и платные API только ради косметического переноса.

Особо защищаемые совместимости: stable command/allocation IDs; generation; попытки; порядок verification sequence; final digest и sealed receipts; missing versus null; executable bit; сетевые и секретные ограничения.

Это предварительная оценка трудоёмкости, не коммерческое обязательство. Единица — рабочий день опытного Python-разработчика с ревью. Скорость генерации кода ИИ не заменяет время проверки совместимости и передачи человеку.

|---|---|---|---:|

Практический порядок PR: baseline/checks → чистое форматирование → API DTO → внутренние типы/порты → diagnostics → источники/поставка → стадии/VM execution → workflow/persistence → journals → panel → документация и человеческая проверка. Допустимо объединять соседние маленькие PR, если ревью сохраняет один понятный предмет.

| Неформальная передача знания | Измеримая самостоятельность нового разработчика | Время настоящего независимого человека и устранение выявленных пробелов |

## 8. Общая приёмка

Работа принимается при одновременном выполнении:

- Все M01–M10 закрыты наблюдаемыми свидетельствами; требование не закрывается фактом создания файла.
- Существующие 196 тестовых случаев сохраняют смысл. Разрешены перенос/переименование и усиление тестов; уменьшение покрытия сценариев скрывать нельзя. В финальном CI обязательные интеграционные проверки не skipped.
- Все затронутые контракты проходят positive/negative проверки; старые fixtures читаются, сохранённые хеши/идентичности не изменились.
- Новые/выделенные границы типизированы; формат/линтер/type checks обязательны. Исключения конкретны и объяснены.
- Нет циклических зависимостей между целевыми пакетами; HTTP handlers не исполняют внутреннюю orchestration самостоятельно; workflow не делает внешнее I/O в DB-транзакции.
- Добавлены проверки опасных путей, изменённых рефакторингом; повторы/UNKNOWN/cancel/fencing проверены по эффектам и числу вызовов.
- Независимый человек прошёл M10 на финальном SHA, а не на предыдущей сборке. Невыполненный человеческий gate оставляет статус «рефакторинг технически проверен, человеческая передача не подтверждена».
- Остаточные live-ограничения перечислены честно. Успешная проверка v2c не выдаётся за испытанный перенос LeraBack или другого клиентского приложения.

Не считать самостоятельными критериями успеха: число созданных папок, лимит строк в каждом файле, процент тестового покрытия без перечня рисков, количество комментариев или согласие ИИ с архитектурой.

## 9. ACTIVE_CONTRACT / TASK_STATE

**ACTIVE_CONTRACT:** оценить актуальный v2c и подготовить техническое задание, направленное на сопровождение человеком. Разрешены чтение, локальные испытания и создание документа. Внедрение/публикация изменений в этот заказ не входят.

**TASK_STATE:**

- `VERIFIED`: исходная версия, размеры/контрактные пробы, локальные тесты с указанными пропусками, CI и отсутствие защиты main на момент чтения.
- `PREPARED`: требования, целевые границы, зависимости, критерии, переход и оценка трудоёмкости.
- `NOT_EXECUTED`: рефакторинг, изменение GitHub rules, обновление серверов, M10 с независимым человеком.
- Следующий шаг исполнения: начать с M01 и фиксации baseline-контрактов; не начинать с механического распиливания `pipeline.py`.
