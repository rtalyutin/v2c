# ADR 0001: сохранить границы исполнения и долговечного состояния

Дата: 2026-10-27. Статус: принято в реализации рефакторинга сопровождаемости. Область: сам v2c; это не подтверждение production rollout или человеческой приёмки.

## Контекст

[ТЗ](../maintenance/specification.md) требует уменьшить объём контекста для безопасного изменения без смены продукта и wire-поведения. До рефакторинга уже существовали отдельный runner, один активный run, EAV метаданных и долговечные команды. Основная обнаруженная проблема — смешение владельцев правил и неявные контракты; необходимость заменить эти четыре механизма не установлена.

## Решение

- Сохранить исполнение кода входящего проекта в runner отдельной VM. API/worker управляют этим исполнением через проверяемый протокол. Выделение [runner](../../src/v2c/runner) и [Timeweb provider](../../src/v2c/providers/timeweb) меняет организацию кода, не доверенную границу процесса.
- Сохранить один активный run и общий runtime lock. [Engine](../../src/v2c/engine.py) и [ControlDatabase](../../src/v2c/persistence/unit_of_work.py) остаются владельцами атомарных guards/записей. Извлечение stores не должно создавать независимые commits внутри одного перехода.
- Сохранить существующую EAV-схему, изолировав проекты/метаданные за [MetadataStore](../../src/v2c/persistence/metadata.py). Не мигрировать данные ради внешнего вида ORM-модели.
- Сохранить durable command protocol: намерение до dispatch, стабильный ID и hash запроса, readback после потерянного ответа, generation fencing и явный `UNKNOWN`. Словари состояний control, runner и gateway остаются раздельными.

## Рассмотренные альтернативы

Исполнение проекта внутри worker сократило бы число процессов, но объединило бы недоверенный код с управляющими данными и секретами. Это противоречит существующей изоляции.

Параллельные активные runs повысили бы потенциальную пропускную способность, но потребовали бы нового протокола ресурсов, блокировок и восстановления. Цель текущей работы не задаёт требования такой производительности.

Замена EAV типизированными таблицами могла бы упростить отдельные запросы, но требует отдельного анализа модели метаданных и миграции сохранённых данных. Текущий интерфейс позволяет локализовать это будущее решение.

Перевод workflow на универсальный движок или повтор команды по одному timeout добавил бы новое поведение. Движок не отменяет необходимости атомарных guards и проверки внешнего эффекта; слепой повтор допускает дублирование эффекта. Для нынешнего набора этапов достаточно явного реестра Pipeline и узких операций.

## Последствия и пересмотр

Сохраняются ограничения пропускной способности, несколько журналов и необходимость reconciliation. Взамен изменение структуры не требует переписывать сохранённые данные или заново определять права на повтор. Старые модульные entrypoints поддерживаются до миграции их развёрнутых потребителей.

Пересмотреть решение можно при измеренном требовании параллельного исполнения, новой модели метаданных или иной границе доверия. Такой проект должен отдельно задать миграцию/rollback, совместимость старых journals и тесты отказов. Ни размер файла, ни количество каталогов сами по себе не являются основанием.

Доказательства безопасности изменений находятся в тестах конкуренции, fencing, retries, lost-response/restart/cancel и [актуальном отчёте проверок](../verification.md). Они не доказывают удобство сопровождения человеком; M10 остаётся отдельной проверкой.
